GPU-accelerated MPC on a real robot arm

Master's thesis at KIT · 2026 · CUDA/C++, Python, ROS 2

In simulation, the TIAGo Pro's right arm writes “MPC” while dodging a falling object under model predictive control.

Model predictive control lets a robot react to disturbances by re-optimising its motion many times per second. On a mobile robot, each optimisation has to finish within milliseconds on the computer the robot carries. GATO is a GPU trajectory optimiser that its authors had run only on desktop GPUs. For my master's thesis I built a model predictive controller around it for the right arm of a TIAGo Pro and ran it on the NVIDIA Jetson AGX Orin in the robot's backpack. The solve times allow about 500 control updates per second, and the arm tracks trajectories in simulation and on the real robot, though less accurately on the real one. Porting GATO turned up defects in it. I reported them upstream and fixed several myself.

How I built it

The controller around GATO, redrawn from Figure 12 of the thesis.

Two preparation steps run once, before control. The first reduces the robot description to the seven arm joints on a fixed base and lumps the gripper into one tool link, so that GRiD can generate the dynamics code that GATO compiles in. The second replaces the collision meshes with simpler enclosing ones and keeps a reviewed list of the body pairs that can't collide.

At runtime the controller runs as three processes. The planning process calls GATO in a loop and starts each solve as soon as the previous one ends. The execution controller samples the newest plan and sends joint torques through ROS 2 at a configurable rate. Two latest-value buffers between them hold only the newest state and the newest plan, so a slow solve never delays a torque command. I used processes rather than threads because GATO's Python interface holds the global interpreter lock for the whole solve, which would stall the thread that sends the torques.

The safety monitor is the third process. It follows the Simplex architecture, in which simple checks decide when a trusted controller takes over from a complex one. Here MPC is the complex controller and the robot's default position controller the trusted one. The monitor checks each new state against the joint limits, a minimum clearance for every checked pair of bodies and a speed limit for every point of the arm. The execution controller rejects plans with non-finite values or torques above 26 Nm and notices when states or plans stop arriving. Any failed check hands the arm back to the position controller. The simplified meshes have about 96% fewer triangles, so the monitor checks every pair that involves the arm at about 60 Hz on the Jetson.

My contributions to GATO

GATO had not been used on a robot like the TIAGo before, and the port exposed defects. I fixed several in pull requests and reported others in issues, many of them after I had submitted the thesis. The maintainer merged my pull requests and acted on my issues.

Correctness

  • Terminal cost (#17). The solver took the terminal cost at the second-to-last state and with the running weight, so changing the terminal weight had no effect.
  • Race in the Schur assembly (#18). Thread blocks overwrote Hessian blocks with their inverses while a neighbouring block still read them, so the result depended on the order in which the GPU ran them. I store the inverses in a separate buffer. As a side effect, batches of 8 problems became about 35% faster on a GTX 1070.
  • Mixed joint axes (#21). On arms whose joints turn about mixed axes, GATO's generic dynamics failed to launch, because the scratch memory for GRiD's helper routines was never allocated. The fix comes with a regression test against Pinocchio.
  • Memory offsets in the dynamics wrappers (#16). The forward dynamics of the bundled robots used the wrong memory layout and crashed the figure-eight benchmark. The maintainer's fix credits me as co-author.
  • Signed joint axes (#22). GRiD's old Python reference dynamics ignored negative joint axes. The maintainer retired it and added tests for signed axes.

Performance

  • Force estimation on embedded GPUs. GATO estimates an external force by solving a batch of trajectory optimisations, one per force hypothesis. On the Jetson a batch of 16 takes several times as long as a single solve. I batch only the dynamics to pick the hypothesis and then optimise once. A control update takes 13.0 instead of 44.9 ms, and the arm compensates an external force as well as before. This change is part of my thesis code, not of upstream GATO.
  • Merit evaluation on embedded GPUs (#19). Profiling on the Jetson showed that the merit evaluation of the line search dominates batched solves. My measurements led to smaller thread blocks for it on embedded GPUs, which the maintainer made the default. A batch of 16 solves for GATO's Indy7 arm went from 63.9 to 34.2 ms (32 knot points, eight SQP iterations). Compared with my thesis version, the current GATO with the current TIAGo model allows 558 instead of 448 control updates per second at 32 knot points, and 194 instead of 103 for a batch of 8.
  • Direct solver on the Jetson (#19). My sweeps showed that GATO's direct solver returned its starting point unchanged on the Jetson. The maintainer fixed the cause, and my reruns were the basis for the new default, which uses the direct solver from 256 knot points.
  • Collision checks in ADMM (#25). GATO evaluated the collision rows in every ADMM inner iteration, although they change only once per SQP iteration. Caching them cut a solve with 250 obstacle primitives from 24.9 to 4.1 ms on a GTX 1070.
  • Moving targets (#26). I measured that re-applying the cost menu for every new target costs up to 296 µs of host time. The maintainer added an update for targets only.

Build, workflow and robot support

  • Setup on a clean system (#15). The installer called a build target that didn't exist, and the CMake requirement didn't match. The maintainer's fix credits me as co-author.
  • CMake version (#23). On the Jetson the build failed because the declared minimum CMake version was too old for the features it uses. I reported it and tested the fix.
  • Solver settings in experiment records (#24). GATO now reports its ADMM iteration budget, so a recorded run holds the complete solver configuration.
  • TIAGo Pro support (#20). Hard Coulomb friction stalled the controller on the TIAGo. My report, my task-cost requirements and measured TIAGo parameters led to smooth friction, the cost menu and rotor-inertia support in GATO. The maintainer implemented them, and the rotor-inertia support builds on code I supplied.
  • In my thesis fork I made the build reproducible with a lockfile that also covers the Jetson's ARM processor, enabled CUDA error checks in release builds and added automated tests to the build. GATO has since added its own test suite and an installation without containers.

Results

46.4 mm
RMS error on the real arm for a 24 s figure-eight, 19.4 mm in GATO's simulation
  • With one SQP iteration per update, the solve times on the Jetson allow 623 control updates per second at 16 knot points and 448 at 32. With up to five SQP iterations, about 150 remain at 32 knot points. For horizons of several seconds (128 knot points), one iteration still allows more than 100.
  • In GATO's simulation the Jetson tracks as accurately as desktop GPUs up to 64 knot points. In Gazebo and on the real arm, control works end to end, but the error is larger: 62.9 mm in Gazebo and 46.4 mm on the arm. On the arm, the controller with its default weights reached none of three test goals, and with higher weights the nearest one within 0.6 s. One explanation is joint losses such as friction, which my prediction model leaves out.
  • After the thesis, in simulation with joint friction, friction feedforward and PD feedback at execution cut the error of a 6 s figure-eight from 52.2 to 7.0 mm. This still has to be tested on the real arm.
  • In Gazebo I injected 19 kinds of faults in 30 trials. In most of them the safety architecture caught the fault and handed the arm back in time. A fault in the execution controller itself isn't covered, because that process runs the fault response.
  • What didn't work: batches of initial guesses (multi-start) found better motions in tuned experiments, e.g. around a moving obstacle, but didn't reach more goals in general.

My role

A solo master's thesis: I did the integration, the experiments and the writing, and the GATO maintainers reviewed and adopted my upstream contributions. I used Claude Code, OpenAI Codex and GitHub Copilot for text and code, and reviewed and tested all core code myself. The pull requests and issues say so too.

Before the thesis: MPCGPU

In the lab course Mathematical and Computational Methods in Robotics and AI I reproduced the GPU solver MPCGPU for model predictive control, instrumented it (kernel timing, VRAM logging) and wrote CUDA line-search variants, with automated experiments on the HPC cluster. The groundwork for my master's thesis.
